## Ownership

Payments have two separate surfaces:

- studio finance: client money against bookings, payment schedules, receipts, and invoices
- SaaS billing: subscription checkout, customer portal, purchases, and plan changes for the app itself

Keep these separate. Studio finance lives under `studioPayments`, `invoices`, and `receipts`.
SaaS billing lives under `payments`.

| Area | Source |
| --- | --- |
| Studio payments router | `packages/api/modules/studio-payments/router.ts` |
| Studio payment schemas | `packages/api/modules/studio/schemas/payment.ts` |
| Invoice router | `packages/api/modules/invoices/router.ts` |

## Database Shape

| Table | Owns | Notes |
| --- | --- | --- |
| `received_amounts` | Actual money received from clients. | Linked to booking, optional schedule, optional invoice. |
| `payment_schedules` | Expected/milestone payments. | Tracks amount, paid amount, due date, status, and tax type. |
| `receipts` | Receipt documents for received payments. | Immutable after creation; void means soft delete. |
| `invoices` | Invoice headers and cached totals. | Covered in [Invoices API](/docs/api/invoices). |
| `invoice_line_items` | Invoice billable rows. | Covered in [Invoices API](/docs/api/invoices). |
| `purchases` | SaaS product/subscription ownership. | User or organization scoped; Dodo-backed. |
| `webhook_events` | Provider webhook idempotency/audit. | Stores raw provider payload and processing status. |

Important constraints:

| Constraint/index | Purpose |
| --- | --- |
| `received_amounts_amount_positive` | Payment amount must be greater than zero. |
| `received_amounts_schedule_idx` | Finds payments linked to a schedule. |
| `received_amounts_invoice_idx` | Finds payments linked to an invoice. |
| `payment_schedules_paid_amount_range` | Paid amount must stay between zero and schedule amount. |
| `payment_schedules_status_idx` | Schedule status filtering. |
| `receipts_org_number_idx` | Active receipt number is unique per organization. |
| `purchases.subscriptionId` unique | One purchase row per provider subscription. |
| `purchases.paymentId` unique | One purchase row per provider payment. |

Enums:

- payment method: `cash`, `upi`, `bank_transfer`, `cheque`, `card`, `other`
- schedule status: `pending`, `partial`, `completed`, `overdue`, `cancelled`
- tax type: `exclusive`, `inclusive`, `no_gst`

## Read Contracts

`listReceived` accepts:

- `bookingId`
- `paymentMethod`
- `dateFrom`, `dateTo`
- `search` over booking name or transaction reference
- pagination, sorting, and `includeDeleted`

`listReceived` returns base received amount fields plus:

- `bookingName`
- `bookingReferenceNumber`
- `scheduleName`
- `receiptId`
- `receiptNumber`

`getReceived` returns the base received amount plus:

- `booking`: `id`, `name`, `referenceNumber`
- `schedule`: `id`, `name` when linked

`listSchedules` accepts:

- `bookingId`
- `status`
- `dueDateFrom`, `dueDateTo`
- `search` over schedule or booking name
- pagination, sorting, and `includeDeleted`

`listSchedules` returns base schedule fields plus:

- `bookingName`
- `bookingReferenceNumber`
- `invoiceId`
- `invoiceNumber`
- `receiptId`
- `receiptNumber`

`getSchedule` returns the base schedule plus:

- `booking`: `id`, `name`, `referenceNumber`
- `invoiceId`, `invoiceNumber`
- `linkedPayments`: received payment id, amount, date, method

`stats` returns:

- `totalReceived`
- `totalScheduled`
- `totalPending`
- `totalOverdue`
- `receivedThisMonth`
- `byPaymentMethod`
- `byScheduleStatus`
- `upcomingSchedules`

## Create Contract

`createReceived` requires:

- `bookingId`
- `amount`
- `paymentMethod`
- `receivedDate`

Optional fields:

- `transactionReference`
- `notes`
- `proofAttachment`
- `paymentScheduleId`
- `invoiceId`

Create behavior:

- verifies booking belongs to active organization and is not deleted
- verifies linked schedule belongs to the same booking
- verifies linked invoice belongs to the same booking
- validates proof attachment keys start with `orgs/{organizationId}/`
- inserts `received_amounts`
- increments `bookings.totalReceived`
- updates linked schedule paid amount and status
- creates a receipt when linked to an invoice
- updates linked invoice payment status
- tracks non-blocking `payment_received` activity

`createSchedule` requires:

- `bookingId`
- `name`
- `amount`
- `dueDate`

Optional fields:

- `taxType`
- `notes`
- `sortOrder`

Create behavior:

- verifies booking belongs to active organization and is not deleted
- computes left-to-schedule as package cost minus received minus pending outstanding
- rejects schedules above remaining balance
- creates a `pending` schedule with `paidAmount = 0`
- tracks non-blocking activity

## Update/Delete Contract

`updateReceived` can change:

- `amount`
- `paymentMethod`
- `transactionReference`
- `receivedDate`
- `notes`
- `proofAttachment`

Amount changes:

- update `bookings.totalReceived` by the delta
- recompute linked schedule `paidAmount`, `status`, and `paidAt`
- reject if linked received payments exceed the schedule amount

`deleteReceived`:

- soft-deletes the received amount
- subtracts payment amount from `bookings.totalReceived`
- recomputes linked schedule totals and status
- tracks non-blocking delete activity

`updateSchedule` can change:

- `name`
- `amount`
- `dueDate`
- `taxType`
- `notes`
- `sortOrder`

Only pending schedules can be modified. Partial, completed, and cancelled schedules are locked.

`deleteSchedule` soft-deletes only pending schedules. Partial, completed, and cancelled schedules are
rejected.

## Convert Schedule Contract

`convertSchedule` marks a schedule as paid or partially paid by creating a received payment.

Behavior:

- rejects cancelled schedules
- returns existing conversion for already partial/completed schedules when a received payment exists
- rejects amounts above remaining scheduled balance
- creates `received_amounts`
- updates schedule `paidAmount`, `status`, and `paidAt`
- if a linked invoice exists, moves draft invoice to sent, updates invoice payment status, and creates a receipt
- retries receipt number generation on unique conflicts

These procedures use `protectedProcedure`, not studio permissions.

## Related Surfaces

| Surface | Relationship |
| --- | --- |
| Bookings | Payment schedules and received payments belong to bookings; booking totals are cached. |
| Invoices | Invoices can be linked to schedules and received payments. |
| Receipts | Generated from invoice-linked payments or manually from received payments. |
| Expenses | Finance reports combine income and expenses. |
| Dashboard | Uses finance totals, payment aging, and recent payment state. |
| Activities | Payment and schedule creates/updates/deletes are tracked non-blockingly. |

## Change Checklist

When changing payment behavior:

- update `packages/api/modules/studio/schemas/payment.ts`
- update `packages/database/drizzle/schema/studio.ts` and migrations for finance table changes
- update `packages/api/modules/studio-payments/procedures/*`
- update invoice/receipt helpers if invoice-linked payment behavior changes
- update booking totals logic and regression tests when changing amount math
- update booking payment form, payments table, filters, and exports
- update this page in the same PR

## Known Gaps

- `updateReceived` does not update receipt rows when amount/date/method changes after receipt creation.
- `deleteReceived` does not void/delete receipts linked to the received payment.
- `createReceived` can link a schedule and invoice independently; it validates each belongs to the booking, but not that the invoice is tied to the same schedule.
- `listReceived` and `listSchedules` join bookings without filtering deleted bookings.
- Schedule `overdue` is an enum value, but stats calculate overdue dynamically from due date and status.
- SaaS billing and studio finance both use the word payments; route names must stay explicit to avoid mixing subscription purchases with client payments.
