## Ownership

Shoots are scheduled work blocks under a booking. They own date/time, venue, planning metadata,
status, and crew assignment links. Assignment writes can notify crew, queue SMS, and enqueue calendar
sync jobs.

| Area | Source |
| --- | --- |

## Database Shape

| Table | Owns | Notes |
| --- | --- | --- |
| `shoots` | Core schedule fields, venue, notes, metadata, status, audit columns, soft delete. | Tenant-scoped by `organizationId`; belongs to one booking. |
| `shoot_assignments` | Crew assigned to a shoot with role, lead flag, optional per-shoot rate. | Unique on `shootId`, `crewId`; physically deleted on unassign. |
| `shoot_calendar_events` | Mapping between shoot/crew and Google or ICS calendar delivery. | Used by calendar worker jobs. |
| `calendar_sync_jobs` | Pending calendar create/update/delete/cancel jobs. | Written as non-blocking side effect. |
| `sms_outbox` | Crew assignment SMS queue. | Written only when crew has phone number and `MSG91_FLOW_CREW_ASSIGNMENT` exists. |

Important indexes:

| Index | Purpose |
| --- | --- |
| `shoots_organization_idx` | Tenant filtering. |
| `shoots_booking_idx` | Booking detail and booking-scoped lists. |
| `shoots_date_idx` | Schedule filtering. |
| `shoots_org_date_idx` | Tenant-scoped schedule filtering/sorting. |
| `shoot_assignments_shoot_crew_idx` | Prevent duplicate crew assignment. |
| `shoot_assignments_crew_idx` | Crew-scoped assignment lookup. |

`shoots.status` is text and configurable through settings (`config_type: shoot_status`). Current
API validates only string length, not a fixed enum.

Planning fields are stored in `shoots.metadata` and projected into API responses:

- `requiredCrewCount`
- `additionalServices`

## API Operations

All shoot procedures use `studioProtectedProcedure` and active organization scope.

| Operation | Method/path | Input schema | Output schema | Permission | Notes |
| --- | --- | --- | --- | --- | --- |
| `shoots.list` | `GET /shoots` | `listShootsInputSchema` | `listShootsOutputSchema` | `shoot:list` | Paginated list with booking info and assigned crew summary. |
| `shoots.listMinimal` | `GET /shoots/minimal` | `listShootsMinimalInputSchema` | `listShootsMinimalOutputSchema` | `shoot:list` | Max 100 records for dropdown/reference use. |
| `shoots.get` | `GET /shoots/{id}` | `getShootInputSchema` | `getShootOutputSchema` | `shoot:read` | Detail with assignments and booking reference. |
| `shoots.create` | `POST /shoots` | `createShootInputSchema` | `createShootOutputSchema` | `shoot:create` | Creates a shoot under an active booking. |
| `shoots.update` | `PUT /shoots/{id}` | `updateShootInputSchema` | `updateShootOutputSchema` | `shoot:update` | Updates schedule fields, metadata, status; may enqueue calendar jobs. |
| `shoots.delete` | `DELETE /shoots/{id}` | `deleteShootInputSchema` | `deleteShootOutputSchema` | `shoot:delete` | Soft delete; may enqueue calendar delete/cancel jobs. |
| `shoots.stats` | `GET /shoots/stats` | `getShootStatsInputSchema` | `getShootStatsOutputSchema` | `shoot:list` | Aggregate counts, optionally booking-scoped. |
| `shoots.assign` | `POST /shoots/{shootId}/assignments` | `assignCrewInputSchema` | `assignCrewOutputSchema` | `shoot:assign` | Creates assignment; may notify, SMS, calendar invite. |
| `shoots.unassign` | `DELETE /shoots/{shootId}/assignments/{crewId}` | `unassignCrewInputSchema` | `unassignCrewOutputSchema` | `shoot:assign` | Deletes assignment; may enqueue calendar delete/cancel. |

## Read Contracts

`list` accepts:

- `bookingId`
- `crewId`
- `status` as string, array, or comma-separated values
- `shootType` as string, array, or comma-separated values
- `dateFrom`, `dateTo`
- `search` over shoot `name` and `venue`
- pagination, sorting, and `includeDeleted`

`list` returns each shoot plus:

- projected planning fields from metadata
- `assignmentsCount`
- `assignedCrew`: crew id/name/avatar
- `bookingName`
- `bookingReferenceNumber`

`listMinimal` accepts `bookingId`, `status`, and `search`; returns `id`, `name`, `shootType`,
`shootDate`, `status`, `bookingId`, sorted by newest shoot date, limited to 100.

`get` returns the base shoot plus:

- projected planning fields from metadata
- assignments with crew id/name/phone
- booking id/name/reference number

`stats` returns:

- `totalShoots`
- `byStatus`
- `upcomingShoots`, excluding `completed` and `cancelled`
- `completedShoots`
- `shootsThisMonth`, based on organization timezone

## Create Contract

Required fields:

- `bookingId`
- `name`
- `shootType`
- `shootDate`

Optional fields:

- `startTime`, `endTime`
- `venue`, `venueAddress`
- `notes`
- `requiredCrewCount`
- `additionalServices`
- `status`

Create behavior:

- verifies booking exists, belongs to active organization, and is not deleted
- stores planning fields in `metadata`
- defaults status to `scheduled`
- tracks non-blocking `created` activity under the parent booking
- auto-subscribes creator to the shoot

Create does not assign crew. Use `shoots.assign` after creation or booking-create embedded shoot
helpers when creating a booking.

## Update Contract

Updatable fields:

- `name`
- `shootType`
- `shootDate`
- `startTime`, `endTime`
- `venue`, `venueAddress`
- `notes`
- `requiredCrewCount`
- `additionalServices`
- `status`

Update behavior:

- verifies shoot belongs to active organization
- merges planning fields into `metadata`
- tracks status changes separately from other field changes
- notifies subscribers on status change
- enqueues calendar jobs when schedule/location fields change or status changes

Calendar-relevant fields:

- `name`
- `shootType`
- `shootDate`
- `startTime`
- `venue`
- `venueAddress`
- `notes`

If the effective status is terminal, existing calendar mappings get delete/cancel jobs. Otherwise
assigned crew with connected Google Calendar get Google create/update jobs, and non-user crew with
email get ICS invite/update jobs.

## Delete Contract

`delete` soft-deletes the shoot by setting:

- `deletedAt`
- `deletedBy`
- `updatedAt`
- `updatedBy`

It rejects already-deleted shoots. It also checks existing calendar mappings and enqueues delete or
cancel jobs. Activity tracking records the deletion under the parent booking.

## Assignment Contract

`assign` requires:

- `shootId`
- `crewId`

Optional:

- `role`, defaults to `Crew`
- `isLead`, defaults to `false`
- `rate`

Assign behavior:

- verifies shoot and crew are active and in the organization
- rejects duplicate crew assignment
- creates `shoot_assignments` row
- tracks assignment activity
- auto-subscribes crew user when linked to an app user
- notifies shoot subscribers
- queues SMS when crew has phone number and assignment flow is configured
- queues Google or ICS calendar invite when possible and shoot status is not terminal

`unassign` deletes the assignment row and may queue calendar delete/cancel based on existing mapping.

## Related Surfaces

| Surface | Relationship |
| --- | --- |
| Bookings | Every shoot belongs to a booking. |
| Crews | Shoot assignments reference crew rows. |
| Calendar worker | Processes `calendar_sync_jobs` written by assign/update/delete/unassign. |
| SMS worker | Sends queued assignment messages from `sms_outbox`. |
| Notifications | Assignment and status changes notify subscribers. |
| Activities | Create, update, status change, delete, assign, unassign are tracked non-blockingly. |
| Settings | Shoot status and shoot type values are configurable settings. |

## Change Checklist

When changing shoot behavior:

- update `packages/api/modules/studio/schemas/shoot.ts`
- update procedure route metadata and side-effect notes
- update DB schema/migration if fields, metadata, indexes, or delete behavior change
- update calendar sync tests when assignment/update/delete side effects change
- update SMS/notification expectations when assignment behavior changes
- update frontend API helpers, forms, table columns, filters, and exports when shapes change
- update this page in the same PR

## Known Gaps

- `status` is configurable text; API does not validate against configuration values yet.
- `shootType` is text; API does not validate against configuration values yet.
- `get` does not exclude soft-deleted shoots.
- `update` and `get` include deleted shoots unless callers avoid those IDs.
- Assignment delete is physical, not soft delete.
