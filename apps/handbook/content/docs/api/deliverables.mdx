## Ownership

Deliverables are the final output commitments for a booking: albums, videos, photo sets, edits, or
custom package items. They own package quantity/cost, due dates, delivery status, review workflow
status, crew assignments, submissions, and conversion into production tasks.

## Database Shape

| Table | Owns | Notes |
| --- | --- | --- |
| `deliverables` | Core fields, `trackingMode`, workflow state, separate completion/delivery dates, metadata, audit columns, soft delete. | `direct` mode uses deliverable assignments; `task_based` mode uses required links. |
| `deliverable_assignments` | Crew assigned directly to a deliverable, including assignment progress and blocker note/timestamps. | Unique on `deliverableId`, `crewId`; not used in task-based mode. |
| `deliverable_task_links` | Relational many-to-many links to tasks, with `required`, `optional`, or `reference` kind. | Composite foreign keys enforce the same organization and booking. Only required links roll up. |
| `assignment_submissions` | Crew work submissions for tasks or deliverables. | Polymorphic check requires exactly one of `taskId` or `deliverableId`. |
| `submission_files` | Files attached to a submission. | Cascades with submission. |
| `submission_feedback` | Review comments/ratings on submissions. | Rating constrained to 1-5 when present. |
| `tasks` / `task_assignments` | Production work linked to deliverables. | Conversion moves direct assignments to the generated required task. |

Important indexes:

| Index | Purpose |
| --- | --- |
| `deliverables_organization_idx` | Tenant filtering. |
| `deliverables_booking_idx` | Booking-scoped lists/details. |
| `deliverables_org_status_idx` | Configurable status filtering. |
| `deliverables_org_workflow_idx` | Review workflow filtering. |
| `deliverables_due_date_idx` | Due-date filtering/sorting. |
| `deliverable_assignments_del_crew_idx` | Prevent duplicate crew assignment. |
| `deliverable_assignments_crew_idx` | Crew-scoped assignment lookup. |
| `assignment_submissions_*` | Submission queue filters by org, task, deliverable, crew, status. |

Status fields:

| Field | Type | Source |
| --- | --- | --- |
| `status` | text | Configurable via settings (`config_type: deliverable_status`). |
| `workflowStatus` | enum | System workflow: `not_started`, `assigned`, `in_progress`, `blocked`, `submitted`, `in_review`, `revision_requested`, `ready`, `approved`. |
| `trackingMode` | enum | `direct` or `task_based`; selected by required task-link presence. |
| `completedAt` | timestamp | Internal completion: approval in direct mode, all required tasks approved in task-based mode. |
| `deliveredAt` | timestamp | Explicit client-delivery event; never set by internal approval. |
| `deliverable_assignments.progressStatus` | enum | Crew-owned state: `assigned`, `in_progress`, `blocked`. |
| `assignment_submissions.status` | enum | Submission state: `draft`, `submitted`, `in_review`, `approved`, `rejected`, `revision_requested`. |

## API Operations

All deliverable procedures use `studioProtectedProcedure` and active organization scope.

| Operation | Method/path | Input schema | Output schema | Permission | Notes |
| --- | --- | --- | --- | --- | --- |

| `deliverables.get` | `GET /deliverables/{id}` | `getDeliverableInputSchema` | `getDeliverableOutputSchema` | `deliverable:read` | Detail with assignments and booking; task links require `task:read`. |
| `deliverables.create` | `POST /deliverables` | `createDeliverableInputSchema` | `createDeliverableOutputSchema` | `deliverable:create` | Creates one custom deliverable under an active booking. |
| `deliverables.update` | `PUT /deliverables/{id}` | `updateDeliverableInputSchema` | `updateDeliverableOutputSchema` | `deliverable:update` | Updates fields and notifies on status change. |
| `deliverables.delete` | `DELETE /deliverables/{id}` | `deleteDeliverableInputSchema` | `deleteDeliverableOutputSchema` | `deliverable:delete` | Soft delete. |

| `deliverables.updateAssignmentStatus` | `PUT /deliverables/{id}/assignment-status` | `updateDeliverableAssignmentStatusInputSchema` | `updateDeliverableAssignmentStatusOutputSchema` | `deliverable:submit` | Updates the caller's direct assignment progress. |

| `deliverables.linkTask` | `PUT /deliverables/{deliverableId}/tasks/{taskId}` | `linkTaskToDeliverableInputSchema` | mutation response | `deliverable:update` + `task:read` | Creates an informational same-booking link without changing either workflow. |
| `deliverables.unlinkTask` | `DELETE /deliverables/{deliverableId}/tasks/{taskId}` | `unlinkTaskFromDeliverableInputSchema` | mutation response | `deliverable:update` + `task:read` | Removes informational links; required production links cannot be removed generically. |
| `deliverables.setDelivery` | `PUT /deliverables/{id}/delivery` | `setDeliverableDeliveryInputSchema` | mutation response | `deliverable:update` | Marks an internally complete deliverable delivered, or clears delivery. |

## Read Contracts

`list` accepts:

- `bookingId`
- `status` as string, array, or comma-separated values
- `workflowStatus`
- `dueDateFrom`, `dueDateTo`
- `crewId`
- `search` over deliverable `name`
- pagination, sorting, and `includeDeleted`

`list` returns each deliverable plus:

- `canConvertToTask`, derived before conversion metadata is permission-redacted
- `assignmentsCount`
- `assignedCrew`: crew id/name/avatar
- `bookingName`
- `bookingReferenceNumber`
- `bookingPackageType`

Conversion task IDs in list metadata are redacted unless the caller also has `task:read`.

`listMinimal` accepts:

- `bookingId`
- `workflowStatus`
- `search`
- pagination

It returns `id`, `name`, `status`, `workflowStatus`, `dueDate`, `bookingId`.

`get` returns the base deliverable plus:

- `canConvertToTask`, false for current and legacy conversions
- assignments with crew id/name/phone
- assignment progress state, note, and timestamps
- active task links with link kind and task workflow state when the caller also has `task:read`
- booking id/name/reference number

Without `task:read`, `get` returns an empty `taskLinks` array and redacts `convertedToTaskId` from
metadata.

`stats` returns:

- `totalDeliverables`
- `byStatus`
- `byWorkflowStatus`
- `overdueDeliverables`, where due date is before today and workflow status is neither `approved` nor `ready`
- `deliveredDeliverables`, based on non-null `deliveredAt`
- `deliverablesThisMonth`, based on created date in organization timezone

## Create Contract

Required fields:

- `bookingId`
- `name`

Optional fields:

- `description`
- `quantity`, defaults to `1`
- `cost`
- `status`, defaults to `pending`
- `dueDate`
- `metadata`

Create behavior:

- verifies booking exists, belongs to active organization, and is not deleted
- sets `isPackageIncluded` to `false`
- sets `workflowStatus` to `not_started`
- ignores client-supplied conversion metadata keys
- tracks non-blocking `created` activity under the booking
- auto-subscribes creator to the deliverable

Booking creation can also create embedded deliverables through booking helper code. This standalone
procedure creates one custom deliverable.

## Update Contract

Updatable fields:

- `name`
- `description`
- `quantity`
- `cost`
- `status`
- `dueDate`
- `metadata`

Update behavior:

- verifies deliverable exists, belongs to active organization, and is not deleted
- updates only non-undefined fields
- preserves system-owned `convertedToTaskId` and `convertedAt` metadata keys
- tracks status changes separately from other field changes
- notifies subscribers on status change

Update does not change `workflowStatus`; workflow changes happen through assignment, submission,
review, or dedicated workflow procedures.

## Assignment Contract

`assign` requires:

- `deliverableId`
- `crewId`

Optional:

- `isLead`, defaults to `false`

Assign behavior:

- verifies deliverable and crew are active and in the organization
- rejects duplicate assignment
- creates `deliverable_assignments` row
- moves `workflowStatus` from `not_started` to `assigned` for first assignment
- tracks assignment activity
- auto-subscribes linked crew user
- notifies subscribers

`unassign` physically deletes the assignment row. If no assignments remain and workflow status is
`assigned`, the deliverable reverts to `not_started`.

## Submission Contract

`submit` requires the current user to be linked to an active crew row and assigned to the
deliverable.

Input:

- `deliverableId`
- optional `submissionNote`
- optional `submissionLinks`
- optional uploaded `files`

Submit behavior:

- rejects if current user is not a crew member
- rejects if the crew member is not assigned to the deliverable
- rejects if the crew already has an active `submitted` or `in_review` submission
- creates `assignment_submissions` row with status `submitted`
- creates `submission_files` rows for uploaded files
- moves deliverable `workflowStatus` to `submitted`
- tracks submission activity
- notifies subscribers with `review_requested`

`updateAssignmentStatus` accepts `assigned`, `in_progress`, or `blocked` plus an optional note. It
writes only the caller's assignment row, then recomputes the parent workflow transactionally.

Multi-assignee precedence is deterministic: approved evidence overrides that assignee's progress;
across assignees `blocked` wins, followed by revision requested, in review, submitted, in progress,
then assigned. Direct submissions are rejected when `trackingMode` is `task_based`.

## Task Link and Rollup Contract

- Ordinary `linkTask` links are informational references; task and deliverable statuses, assignments, and workflows remain independent.
- Required links are created only by the explicit `convertToTask` workflow and switch the deliverable to `task_based`.
- Conversion to a required link is rejected while direct submissions exist; direct assignments move to the generated task.
- Same organization and booking are checked in the procedure and enforced by composite foreign keys.
- Required task states roll up automatically whenever task assignment/submission/review state changes.
- All required tasks approved produces deliverable `ready` and sets `completedAt`.
- Regression clears `completedAt`; `deliveredAt` remains an explicit historical delivery event.
- A delivered deliverable that later regresses is intentionally not silently undelivered. The detail
  UI surfaces the inconsistency and keeps the clear-delivery action available.
- Generic unlinking is limited to informational links. Required production links are protected;
  reversing conversion requires a future explicit undo-conversion workflow.
- Soft-deleting a deliverable removes its task-link rows in the same transaction.
- Shoot relationships remain reference-only; shoots do not drive deliverable status.

Legacy migration note: before this contract, internal approval was the only application workflow
that wrote `deliveredAt`. Migration `0046` moves those timestamps to `completedAt` and clears
`deliveredAt`; preserving them as client deliveries would retain false delivery history. Existing
delivered counts therefore reset to explicit client-delivery events after migration.

## Convert To Task Contract

`convertToTask` creates a production task from a deliverable.

Input:

- `deliverableId`
- optional `taskName`, defaults to `Task: <deliverable name>`
- optional `taskDescription`, defaults to deliverable description
- optional `taskPriority`, defaults to `normal`
- optional `taskDueDate`, defaults to deliverable due date

Conversion behavior:

- requires both `deliverable:update` and `task:create`
- locks the deliverable row with `FOR UPDATE`
- rejects deleted or already-converted deliverables
- creates a task under the same booking
- rejects deliverables that already have direct submissions
- moves deliverable assignments, including progress, to task assignments
- creates a required relational link and switches the deliverable to task-based tracking
- moves task workflow to `assigned` if assignments were copied
- writes `convertedToTaskId` and `convertedAt` into deliverable metadata
- tracks task creation and deliverable conversion activity
- auto-subscribes converter to the new task

## Delete Contract

`delete` soft-deletes the deliverable by setting:

- `deletedAt`
- `deletedBy`
- `updatedAt`
- `updatedBy`

It verifies the deliverable is active and belongs to the organization, locks it, removes task links,
and soft-deletes it in one transaction. Activity tracking records the deletion under the parent
booking.

## Related Surfaces

| Surface | Relationship |
| --- | --- |
| Bookings | Every deliverable belongs to a booking. |
| Crews | Deliverable assignments reference crew rows. |
| Tasks | Conversion creates tasks and copies assignments. |
| Submissions | Assigned crew submit work for review. |
| Files | Submission files store uploaded file metadata. |
| Notifications | Assignment, status change, and submission review request notify subscribers. |
| Activities | Create, update, status change, delete, assign, unassign, submit, convert are tracked non-blockingly. |
| Settings | Deliverable status values are configurable. |

## Change Checklist

When changing deliverable behavior:

- update `packages/api/modules/studio/schemas/deliverable.ts`
- update procedure route metadata and side-effect notes
- update DB schema/migration if fields, workflow enums, indexes, metadata, or delete behavior change
- update submission/review tests when workflow behavior changes
- update task conversion tests when conversion metadata or copied assignments change
- update frontend API helpers, forms, table columns, filters, and exports when shapes change
- update this page in the same PR

## Known Gaps

- `status` is configurable text; API does not validate against configuration values yet.
- `delete` retains assignments/submissions until later physical delete cascades; task-link rows are removed immediately.
- Assignment delete is physical, not soft delete.
- `list` schema allows array status, but string handling does not split comma-separated values.
