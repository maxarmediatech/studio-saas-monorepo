## Ownership

WhatsApp is a partially wired module. The active production-shaped path is Meta Cloud API webhook
ingestion plus a custom outbox worker. It is not a Trigger.dev setup, and the studio-facing
`whatsappRouter` is still not mounted into the main ORPC router.

| Area | Status | Source |
| --- | --- | --- |
| Meta webhook ingress | Active | `packages/api/index.ts`, `packages/api/modules/whatsapp/webhook-handler.ts` |
| Cloud API provider | Active | `packages/whatsapp-providers/src/cloud-api/provider.ts` |
| Outbox delivery worker | Active service, excluded from root `pnpm dev` | `services/whatsapp-worker/src/index.ts` |
| WhatsApp DB schema | Active schema package, re-exported by database | `packages/whatsapp-db/drizzle/schema/*`, `packages/database/drizzle/schema/index.ts` |
| Studio ORPC router | Draft/unmounted | `packages/api/modules/whatsapp/router.ts` |
| Baileys bridge | Placeholder | `services/whatsapp-bridge/src/index.ts` |
| Trigger.dev | Not present | no tracked `@trigger.dev` dependency or `trigger.config.*` |

## Runtime Shape

Current end-to-end Cloud API shape:

1. An account row is created in `wa_accounts` with `provider = cloud_api`, Meta phone number id,
   WABA id, access token, and webhook verify token.
2. Meta calls `GET /api/webhooks/whatsapp/:token` to verify the webhook.
3. Meta calls `POST /api/webhooks/whatsapp/:token` for inbound messages and status updates.
4. Webhook handling resolves the account by `phoneNumberId` plus token, stores a dedupe event in
   `wa_events`, then updates `wa_contacts`, `wa_conversations`, and `wa_messages`.
5. Outbound sends are designed to insert `wa_messages` plus `wa_outbox` rows.
6. `@repo/whatsapp-worker` polls `wa_outbox`, sends through Meta Graph API, and updates
   `wa_outbox` and `wa_messages`.

Important routing detail:

- The webhook endpoint is mounted directly in the Hono API app at `/api/webhooks/whatsapp/:token`.
- Draft ORPC paths such as `/api/whatsapp/messages/send` are not reachable until
  `whatsappRouter` is mounted in `packages/api/orpc/router.ts`.

## Meta Credentials

Cloud API credentials are stored per WhatsApp account row, not as app-level `.env.example` values.

| Field | Stored in | Used by |
| --- | --- | --- |
| `phoneNumberId` | `wa_accounts.phone_number_id` | webhook account resolution, Graph API message URL |
| `wabaId` | `wa_accounts.waba_id` | account metadata/future template sync |
| `accessToken` | `wa_accounts.access_token` | outbound worker Authorization bearer token |
| `webhookVerifyToken` | `wa_accounts.webhook_verify_token` | webhook URL token and Meta verify token comparison |
| `webhookUrl` | `wa_accounts.webhook_url` | schema supports it, current connect procedure does not set it |

Graph API provider behavior:

- default API version is `v22.0`
- sends to `https://graph.facebook.com/{version}/{phoneNumberId}/messages`
- supports text, media, template, and read receipt calls
- returns Meta `messages[0].id` as `providerMessageId`

Security note:

- `accessToken` is stored as plain text in `wa_accounts.access_token`. Before production rollout,
  encrypt this field or move token storage behind a secrets abstraction.

## Webhook Contract

Mounted routes:

| Method/path | Purpose | Behavior |
| --- | --- | --- |
| `GET /api/webhooks/whatsapp/:token` | Meta verification | Requires `hub.mode=subscribe`, `hub.verify_token`, and `hub.challenge`; token must match an account `webhookVerifyToken`. |
| `POST /api/webhooks/whatsapp/:token` | Meta events | Parses Cloud API payload, dedupes via `wa_events`, mutates contacts/conversations/messages, always returns 200 after per-event processing attempts. |

Inbound message behavior:

- creates missing `wa_contacts` by `organizationId`, `accountId`, and WhatsApp id
- creates missing `wa_conversations`
- inserts inbound `wa_messages` with `status = delivered`
- updates conversation last message id/time/preview
- stores the parsed event in `wa_events` and marks it processed or failed

Status update behavior:

- dedupe id is `{providerMessageId}:{status}:{timestamp}`
- finds existing outbound message by `providerMessageId` and account
- updates `wa_messages.status`, `statusUpdatedAt`, `errorCode`, and `errorMessage`
- records failure on the event if the message cannot be found

Current webhook gaps:

- no Meta `X-Hub-Signature-256` app-secret validation
- verification compares the query verify token to the route token, not to a separate account secret
- account fallback by token alone can accept events without matching `phoneNumberId`
- `wa_accounts.lastEventAt` is not updated

## Outbound Send Contract

Draft ORPC procedures exist for:

| Operation | Draft path | Result |
| --- | --- | --- |
| `whatsapp.connectCloudApi` | `POST /whatsapp/accounts/connect-cloud-api` | creates connected Cloud API account with Meta credentials |
| `whatsapp.connectBaileys` | `POST /whatsapp/accounts/connect-baileys` | creates QR-pending Baileys account |
| `whatsapp.sendText` | `POST /whatsapp/messages/send` | creates contact/conversation/message/outbox |
| `whatsapp.sendMedia` | `POST /whatsapp/messages/send-media` | creates media/message/outbox |
| `whatsapp.sendTemplate` | `POST /whatsapp/messages/send-template` | creates message/outbox |

These procedures are studio-protected but currently unreachable through the main app API because
`whatsappRouter` is not mounted.

Expected send lifecycle once mounted:

- validate input via `packages/api/modules/whatsapp/types.ts`
- find or create contact by `organizationId` and `to`
- find or create conversation by `organizationId`, `accountId`, and contact
- insert outbound `wa_messages` with `status = pending`
- insert `wa_outbox`
- worker sends to Meta and marks the message `sent` or `failed`
- Meta webhook later upgrades status to delivered/read/failed

## Worker Contract

The worker is a long-running Node service, not Trigger.dev.

Command:

```bash
pnpm --filter @repo/whatsapp-worker dev
```

Root `pnpm dev` excludes WhatsApp packages and services:

```bash
--filter=!@repo/whatsapp-bridge
--filter=!@repo/whatsapp-db
--filter=!@repo/whatsapp-core
--filter=!@repo/whatsapp-providers
--filter=!@repo/whatsapp-worker
```

Runtime knobs:

| Env var | Default | Meaning |
| --- | --- | --- |
| `WHATSAPP_OUTBOX_INTERVAL_MS` | `5000` | poll interval |
| `WHATSAPP_OUTBOX_BATCH_SIZE` | `10` | max rows per batch |

Worker behavior:

- selects `wa_outbox` rows with `status IN ('pending', 'failed')`
- respects `nextAttemptAt`
- orders by `priority DESC`
- marks row `processing` and increments attempts
- supports `text`, `template`, `image`, `video`, `audio`, `document`, and `sticker`
- only sends accounts with `provider = cloud_api`
- fails rows with missing `accessToken`, missing `phoneNumberId`, missing recipient, or invalid message data
- retries with delay `min(30 * attempts, 15 minutes)` until `maxAttempts`

Worker gaps:

- no transaction claim with `FOR UPDATE SKIP LOCKED`
- no lock owner/timestamp columns
- no stale `processing` recovery
- `setInterval` can overlap long batches
- no tests for claim/retry/exhaustion behavior

## Read APIs

Draft inbox APIs exist but are not mounted:

| Operation | Draft path | Notes |
| --- | --- | --- |
| `whatsapp.listContacts` | `GET /whatsapp/contacts` | cursor pagination and search |
| `whatsapp.listConversations` | `GET /whatsapp/conversations` | filters by account/status/search |
| `whatsapp.getConversation` | `GET /whatsapp/conversations/:conversationId` | includes contact |
| `whatsapp.listMessages` | `GET /whatsapp/conversations/:conversationId/messages` | cursor pagination and media join |
| `whatsapp.markConversationRead` | `POST /whatsapp/conversations/:conversationId/mark-read` | only clears local unread count |

`markConversationRead` does not currently call Meta `markRead`, even though the Cloud API provider
has a `markRead(messageIds)` method.

| Table | Active role |
| --- | --- |
| `wa_accounts` | Meta account credentials, provider type, connection state, webhook token. |
| `wa_contacts` | WhatsApp contact records scoped by organization/account. |
| `wa_conversations` | Account/contact thread state and last-message cache. |
| `wa_messages` | Inbound/outbound message records and provider status. |

| `wa_outbox` | Pending outbound delivery queue. |

## Redundant Or Placeholder Surfaces

Mark these for deletion or hardening before expanding the module:

| Surface | Current state | Recommendation |
| --- | --- | --- |
| `services/whatsapp-bridge` | health route only; all session/send routes return `501 not_implemented` | delete if Baileys is no longer planned, otherwise implement before documenting as supported |
| `connectBaileys` procedure | creates `qr_pending` account only; no working bridge/session flow | keep hidden/unmounted or delete with bridge if Meta-only is the direction |
| `whatsapp.webhook` ORPC procedure | only returns `{ received: true }` | delete or replace with the mounted webhook handler; do not expose both |
| `wa_campaigns` | schema only | keep as planned foundation or remove until campaign API lands |
| `wa_bot_flows` | schema only | keep as planned foundation or remove until bot-flow engine lands |
| empty WhatsApp settings route folders | directories exist without tracked pages | remove if no UI work is planned in this branch |
| Trigger.dev expectation | no tracked source/dependency/config | document as not used, or add real Trigger.dev jobs before referring to it |

## Change Checklist

When changing WhatsApp:

- update this page from actual mounted routes and runnable services, not only file lists
- if mounting `whatsappRouter`, add permissions and update API clients/UI flows
- add Meta app-secret signature verification before production webhook use
- add token encryption or a secrets abstraction for `wa_accounts.accessToken`
- verify webhook GET/POST with a real Meta test payload
- run the outbox worker against a queued row and confirm Graph API response handling
- close worker locking gaps before running multiple worker instances
- update `.env.example` if app-level WhatsApp or Trigger.dev env vars are introduced
