## Ownership

for the app wiring: WhatsApp API procedures are mounted, outbound messages are queued through
Trigger.dev, and Meta credentials come from embedded signup or manual Cloud API connection.

## Runtime Shape

Current Cloud API flow:

1. Studio connects a WhatsApp account through embedded signup or manual Cloud API credentials.
2. Credentials are validated against Meta, encrypted, and stored in `wa_accounts`.
3. Meta calls `GET /api/webhooks/whatsapp/:token` for verification and
   `POST /api/webhooks/whatsapp/:token` for events.
4. Inbound webhook processing writes `wa_events`, `wa_contacts`, `wa_conversations`, and
   `wa_messages`.
5. Send procedures create/update contact and conversation rows, insert `wa_messages`, insert
   `wa_outbox`, then call `triggerWhatsAppOutbox`.
6. `triggerWhatsAppOutbox` calls Trigger.dev task `whatsapp-process-outbox`.
7. Trigger.dev runs `@repo/whatsapp-outbox`, which claims the row, sends through Meta Graph API,
   updates `wa_outbox` and `wa_messages`, and lets Meta webhooks later advance delivery status.
8. Scheduled Trigger.dev recovery task `whatsapp-recover-outbox` re-triggers due pending/failed
   outbox rows.

## Meta Credentials

App-level Meta env on `dev`:

| Env var | Purpose |
| --- | --- |
| `NEXT_PUBLIC_META_APP_ID` | Meta developer app id for embedded signup. |
| `NEXT_PUBLIC_WHATSAPP_EMBEDDED_SIGNUP_CONFIG_ID` | Facebook Login for Business config id. |
| `META_APP_SECRET` | Server-only app secret for token exchange and webhook security. |
| `META_GRAPH_VERSION` | Graph API version, defaulted around `v22.0`. |
| `META_WEBHOOK_VERIFY_TOKEN` | Platform webhook verify token for embedded signup accounts. |

Per-account fields:

| Field | Stored in | Notes |
| --- | --- | --- |
| `phoneNumberId` | `wa_accounts.phone_number_id` | Graph API message URL and webhook account resolution. |
| `wabaId` | `wa_accounts.waba_id` | Business account id and template sync. |
| `accessToken` | `wa_accounts.access_token` | Encrypted with `encryptWhatsAppSecret`. |
| `appSecret` | `wa_accounts.app_secret` | Encrypted when present. |
| `webhookVerifyToken` | `wa_accounts.webhook_verify_token` | Stored as SHA-256 hash. |
| `apiVersion` | `wa_accounts.api_version` | Used by provider/admin calls. |

Manual connection:

- validates `accessToken`, `phoneNumberId`, and optional `wabaId`
- stores encrypted access token and optional encrypted app secret
- hashes the provided webhook verify token
- stores Meta metadata such as verified name, quality rating, messaging tier, and validation time

Embedded signup:

- requires `NEXT_PUBLIC_META_APP_ID`, `META_APP_SECRET`, and `META_WEBHOOK_VERIFY_TOKEN`
- exchanges signup code for access token
- validates account through Meta
- subscribes the WABA to app webhook events
- stores encrypted token/app secret and signup metadata

## Webhook Contract

Mounted routes:

| Method/path | Purpose | Behavior |
| --- | --- | --- |
| `GET /api/webhooks/whatsapp/:token` | Meta verification | Verifies Meta subscription challenge against stored token/hash behavior. |
| `POST /api/webhooks/whatsapp/:token` | Meta events | Parses Cloud API payload, dedupes events, mutates contacts/conversations/messages/statuses. |

Webhook side effects:

- `message.inbound`: ensure contact and conversation, insert inbound message, update conversation
  last-message fields
- `message.status`: find outbound message by provider id and update sent/delivered/read/failed
  state
- `wa_events`: stores provider event id, event type, payload, processed/error state

## Outbound Send Contract

Mounted ORPC operations on `dev` include:

| Operation | Path | Result |
| --- | --- | --- |
| `whatsapp.connectCloudApi` | `POST /whatsapp/accounts/connect-cloud-api` | Manual Cloud API account connection. |
| `whatsapp.completeEmbeddedSignup` | `POST /whatsapp/accounts/embedded-signup/complete` | Embedded signup token exchange, validation, webhook subscription. |
| `whatsapp.sendText` | `POST /whatsapp/messages/send` | Creates outbound text message and queues Trigger.dev send. |
| `whatsapp.sendMedia` | `POST /whatsapp/messages/send-media` | Creates media/message/outbox and queues Trigger.dev send. |
| `whatsapp.sendTemplate` | `POST /whatsapp/messages/send-template` | Creates template message/outbox and queues Trigger.dev send. |
| `whatsapp.retryMessage` | `POST /whatsapp/messages/:messageId/retry` | Resets failed/pending outbox row and queues Trigger.dev send again. |
| `whatsapp.listConversations` | `GET /whatsapp/conversations` | Inbox list. |
| `whatsapp.listMessages` | `GET /whatsapp/conversations/:conversationId/messages` | Thread messages. |
| `whatsapp.listContacts` | `GET /whatsapp/contacts` | Contact list/search. |
| `whatsapp.listTemplates` | `GET /whatsapp/templates` | Synced Meta templates. |
| `whatsapp.syncTemplates` | `POST /whatsapp/templates/sync` | Fetches/upserts Meta templates. |

Send procedure behavior:

- resolves active account with `findActiveWhatsAppAccount`
- creates or updates contact details
- creates or finds conversation
- inserts `wa_messages` with `status = pending`
- records outbound conversation activity
- inserts `wa_outbox`
- calls `triggerWhatsAppOutbox({ outboxId, messageId })`

If Trigger.dev enqueue fails, `triggerWhatsAppOutbox` marks both the outbox row and message failed,
records the enqueue error, and throws back to the API caller.

## Trigger.dev Queue

Trigger config:

| Setting | Value |
| --- | --- |
| Config file | `trigger.config.ts` |
| Project env | `TRIGGER_PROJECT_ID` |
| Secret env | `TRIGGER_SECRET_KEY` |
| Runtime | `node` |
| Task dirs | `./src/trigger` |
| Default retries | 3 attempts, exponential backoff from 1s to 10s, randomized |
| Local command | `pnpm jobs:dev` |
| Deploy command | `pnpm jobs:deploy` |

Tasks:

| Task id | Type | Purpose |
| --- | --- | --- |
| `whatsapp-process-outbox` | `schemaTask` | Process one outbox row by id. Queue concurrency limit: 5. |
| `whatsapp-recover-outbox` | scheduled task | Daily at `0 3 * * *`; fetches due rows and triggers `whatsapp-process-outbox`. |
| `whatsapp-process-outbox-batch` | `schemaTask` | Processes up to `limit` due rows inline. Queue concurrency limit: 1. |

Recovery behavior:

- recovery fetches due `wa_outbox` rows with `status IN ('pending', 'failed')`
- respects `nextAttemptAt`
- skips rows whose attempts reached max attempts
- re-triggers each due row through Trigger.dev
- if re-triggering fails, marks the outbox/message failed via `markWhatsAppOutboxFailure`

## Outbox Processor

`@repo/whatsapp-outbox` owns delivery logic used by Trigger.dev.

Claim behavior:

- updates one due row to `processing`
- increments `attempts`
- clears `nextAttemptAt` and `errorMessage`
- only claims rows in `pending` or `failed`
- only claims rows below `maxAttempts`

Delivery behavior:

- decrypts stored access token before constructing `CloudApiProvider`
- supports text, template, image, video, audio, document, and sticker sends
- signs S3 media URLs before sending when `wa_media.storage_type = s3`
- marks success as `wa_outbox.status = sent`, `wa_messages.status = sent`
- stores Meta provider message id on success
- classifies known auth/permission/recipient/provider errors as permanent
- retryable failures compute `nextAttemptAt = min(30 * attempts, 15 minutes)`
- permanent failures or max-attempt failures do not schedule another retry

Known processor gap:

- claim is an atomic conditional update, but there are no explicit lock owner/timestamp columns.
  Trigger.dev concurrency is the main runtime guard.

## Redundant Or Placeholder Surfaces

Mark these for deletion or hardening:

| Surface | Current state | Recommendation |
| --- | --- | --- |
| `services/whatsapp-worker` | legacy/custom poll worker over `wa_outbox` | delete once all environments use Trigger.dev, or keep only as local fallback with clear docs |
| `packages/whatsapp-outbox` duplicate secret decrypt | decrypts `v1:` tokens locally | keep aligned with `account-secrets`; avoid two encryption implementations drifting |
| `services/whatsapp-bridge` | health route only; session/send routes return `501 not_implemented` | delete if Baileys is not planned |
| `connectBaileys` | creates QR-pending account without complete bridge session flow | hide/delete until Baileys is real |
| `whatsapp.webhook` ORPC procedure | separate draft webhook endpoint | prefer mounted Hono webhook path; avoid duplicate ingress |

## Change Checklist

When changing WhatsApp:

- inspect `dev` branch implementation first if working from another branch
- update Trigger.dev task ids, retry policy, and env docs together
- keep send procedures, `trigger-outbox`, and `@repo/whatsapp-outbox` contract aligned
- verify `pnpm jobs:dev` for local queue testing
- verify webhook GET/POST with Meta test payloads
- update `.env.example` when Meta or Trigger env changes
- do not delete `wa_outbox`; Trigger.dev uses it as durable send state, not as a replacement queue
