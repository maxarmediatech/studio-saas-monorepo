## Purpose

Auth is the entry gate for the SaaS product. It answers five questions:

- Who is the user?
- Which organization are they acting inside?
- Are they a platform admin, organization owner/admin, member, or custom role?
- Which product resources can they read or mutate?
- What happens to dependent systems when membership changes?

The implementation is centered on Better Auth in `packages/auth`, then enforced in web layouts,
middleware, and API procedures.

## Package Map

| Path | Role |
| --- | --- |
| `packages/auth/auth.ts` | Server auth configuration, Better Auth plugins, email flows, session hooks, organization hooks, and exported auth types. |
| `packages/auth/client.ts` | Browser auth client with organization, admin, magic link, two-factor, API key, and dynamic access-control plugins. |
| `packages/auth/lib/permissions.ts` | Resource/action matrix, static roles, custom-role helpers, and permission utilities. |
| `packages/auth/lib/organization.ts` | Side effects tied to membership: auto-create/link crew records and update subscription seats. |
| `packages/auth/lib/organization-roles.ts` | Seeds default editable organization roles. |
| `packages/auth/plugins/invitation-only` | Blocks email signup when public signup is disabled and no pending invite exists. |
| `packages/database/drizzle/schema/auth.ts` | Users, sessions, accounts, verifications, and two-factor tables. |
| `packages/database/drizzle/schema/core.ts` | Organizations, members, teams, invitations, organization roles, purchases, and webhook events. |
| `apps/web/proxy.ts` | Edge-level route protection for `/app` and auth-route availability. |
| `apps/web/modules/saas/auth/lib/server.ts` | Server helpers for session, active organization, organization list, accounts, and invitation lookup. |
| `packages/api/orpc/procedures.ts` | API-level auth gates: public, protected, admin, and studio-protected procedures. |

The ADR is `docs/adr/0004-authentication-strategy.md`, but the live implementation has moved beyond
that early sketch. Treat `packages/auth/auth.ts` as the real source of truth.

## Runtime Shape

The server package exports one Better Auth instance:

```ts
export const auth = betterAuth({
  baseURL: appUrl,
  trustedOrigins: [appUrl],
  database: drizzleAdapter(db, {
    provider: "pg",
    usePlural: true,
  }),
  advanced: {
    database: {
      generateId: false,
    },
  },
  session: {
    expiresIn: config.auth.sessionCookieMaxAge,
    freshAge: 0,
  },
});
```

Important details:

- Database storage is Drizzle/PostgreSQL through `@repo/database`.
- IDs are generated by the database schema, not by Better Auth.
- Session lifetime comes from `config.auth.sessionCookieMaxAge`.
- `freshAge: 0` means sensitive checks should not rely on an implicit "fresh session" window.
- Trusted origins are based on the app base URL.

Server code should import `auth` from `@repo/auth`; client components should import `authClient`
from `@repo/auth/client`.

## Login And Signup

Enabled sign-in methods:

- Email and password.
- Google OAuth.
- Magic link.
- Username plugin support.
- Two-factor plugin support.

Email/password signup behavior depends on config:

```ts
emailAndPassword: {
  enabled: true,
  autoSignIn: !config.auth.enableSignup,
  requireEmailVerification: config.auth.enableSignup,
}
```

When public signup is enabled, new users must verify email. When public signup is disabled, signup is
expected to happen through an invitation and can auto sign in because the invitation already proves
the email target.

The invitation-only plugin enforces that rule:

```ts
if (config.auth.enableSignup) {
  return;
}

const { email } = ctx.body;
const hasInvitation = await getPendingInvitationByEmail(email);

if (!hasInvitation) {
  throw new APIError("BAD_REQUEST", {
    code: "INVALID_INVITATION",
    message: "No invitation found for this email",
  });
}
```

Auth screens live under `apps/web/app/auth`:

- `/auth/login`
- `/auth/signup`
- `/auth/forgot-password`
- `/auth/reset-password`
- `/auth/verify`
- `/auth/complete`
- `/auth/error`

UI forms live in `apps/web/modules/saas/auth/components`.

## Email Flows

Auth email delivery is centralized through `sendAuthEmail()` in `packages/auth/auth.ts`. It logs
delivery failures under `auth.email.send_failed` and uses request cookies to resolve locale.

Current flows:

| Flow | Template |
| --- | --- |
| Email verification | `emailVerification` |
| Change-email verification | `emailVerification` |
| Reset password | `forgotPassword` |
| Magic link | `magicLink` |
| Organization invitation | `organizationInvitation` |

Invitation emails choose destination by user existence:

```ts
const existingUser = await getUserByEmail(email);
const url = new URL(
  existingUser ? "/auth/login" : "/auth/signup",
  getRequestBaseUrl(request) ?? appUrl,
);

url.searchParams.set("invitationId", id);
url.searchParams.set("email", email);
```

If invitation delivery fails, the package throws `OrganizationInvitationEmailDeliveryError` with the
email, invitation id, organization id, and underlying reason.

## Session Resolution

Server components use cached helpers from `apps/web/modules/saas/auth/lib/server.ts`:

```ts
export const getSession = cache(async () => {
  const session = await auth.api.getSession({
    headers: await headers(),
    query: {
      disableCookieCache: true,
    },
  });

  return session;
});
```

`disableCookieCache: true` forces the server helper to read current session state instead of trusting
the cookie cache during SSR.

Related helpers:

```ts
export const getActiveOrganization = cache(async (slug: string) => {
  return auth.api.getFullOrganization({
    query: { organizationSlug: slug },
    headers: await headers(),
  });
});

export const getOrganizationList = cache(async () => {
  return auth.api.listOrganizations({ headers: await headers() });
});
```

Use these helpers in server layouts and pages. Do not call the client auth package from server code.

## Route Protection

There are three layers of protection.

### Proxy

`apps/web/proxy.ts` performs cheap request-level protection:

```ts
if (pathname.startsWith("/app")) {
  if (!sessionCookie) {
    const redirectTo = `${pathname}${search}`;
    return NextResponse.redirect(
      new URL(withQuery("/auth/login", { redirectTo }), origin),
    );
  }
}
```

It also redirects `/app` to the active organization home when the `activeOrganizationSlug` cookie is
available.

### SaaS App Layout

`apps/web/app/(saas)/app/layout.tsx` performs full server validation:

- Requires a session.
- Loads organization list.
- Resolves active organization.
- Enforces onboarding.
- Enforces organization requirement.
- Enforces billing/plan selection when enabled.
- Prefetches session and organization queries for the client.

```ts
const session = await getSession();

if (!session) {
  redirect("/auth/login");
}

if (config.organizations.requireOrganization && !organizationId) {
  redirect(`/new-organization?redirectTo=${encodeURIComponent("/app")}`);
}
```

### Organization Layout

`apps/web/app/(saas)/app/[organizationSlug]/layout.tsx` validates the concrete organization route:

```ts
const [session, organization] = await Promise.all([
  getSession(),
  getActiveOrganization(organizationSlug),
]);

if (!session) redirect("/auth/login");
if (!organization) return notFound();
```

After that it resolves studio capabilities and passes them into `StudioCapabilitiesProvider`.

## Active Organization

The active organization exists in two places:

- `session.session.activeOrganizationId`, owned by Better Auth.
- `activeOrganizationSlug` cookie, set for routing convenience.

Session creation auto-selects the first organization when organizations are enabled:

```ts
const memberships = await getOrganizationsByUserId(session.userId);
const firstOrg = memberships[0]?.organization;

return {
  data: {
    ...session,
    activeOrganizationId: firstOrg?.id ?? null,
  },
};
```

After auth actions that can change organization state, the auth hook refreshes the slug cookie:

- sign in
- sign up
- organization create
- invitation accept
- organization set-active

If no active organization exists, the slug cookie is cleared.

## Organizations, Teams, And Crew

The Better Auth organization plugin is enabled with teams and dynamic access control:

```ts
organization({
  ac,
  roles: appRoles,
  dynamicAccessControl: {
    enabled: true,
    maximumRolesPerOrganization: 20,
  },
  teams: {
    enabled: true,
    allowRemovingAllTeams: true,
    defaultTeam: {
      enabled: false,
    },
  },
});
```

Organization hooks normalize role storage and keep studio data in sync:

- `afterCreateOrganization` seeds editable roles.
- `beforeAddMember` serializes roles to comma-separated storage.
- `afterAddMember` creates or links a `crews` row.
- `beforeCreateInvitation` serializes invitation roles.
- `beforeUpdateMemberRole` serializes updated roles.
- `afterAcceptInvitation` creates or links a `crews` row.

Crew linking is idempotent. `ensureCrewForMember()` first looks for an existing active crew by
`organizationId` and `userId`, then tries to link an email-matched crew with no `userId`, then inserts
a new internal crew profile with `metadata: { autoCreated: true }`.

## Role Model

Permissions are declared as resource/action statements in `packages/auth/lib/permissions.ts`:

```ts
export const statement = {
  dashboard: ["read"],
  booking: ["create", "read", "update", "delete", "list", "reference"],
  client: ["create", "read", "update", "delete", "list"],
  shoot: ["create", "read", "update", "delete", "list", "assign"],
  task: ["create", "read", "update", "delete", "list", "assign", "submit"],
  payment: ["create", "read", "update", "delete", "list", "reference"],
  channel: ["create", "read", "update", "delete", "list"],
  discussion: ["create", "read", "update", "delete", "list"],
} as const;
```

Static Better Auth roles:

| Role | Purpose |
| --- | --- |
| `owner` | Full access including organization management. |
| `admin` | Full access except organization deletion. |
| `member` | Limited access, mainly own work, references, and discussion access. |

Editable organization roles are seeded separately:

| Role | Purpose |
| --- | --- |
| `manager` | Shoots, tasks, deliverables, limited booking/client access. |
| `post_production_manager` | Task and deliverable workflow. |
| `hr` | Crew, expenses, and payments. |

`crew` is a profile-only role. It is filtered out of organization role storage by
`coerceOrganizationRoles()`.

Roles can be stored as strings, arrays, JSON arrays, or comma-separated values. Always use
`normalizeRoles()`, `serializeRoles()`, or `coerceOrganizationRoles()` instead of parsing role strings
by hand.

## Custom Roles

Custom role definitions live in `organizationRoles`. Each row stores:

- `organizationId`
- `role`
- serialized permission JSON
- optional description and color

Server UI capability checks load custom permissions with:

```ts
const customRoles = await db.query.organizationRoles.findMany({
  where: (rolesTable, { and, eq, inArray }) =>
    and(
      eq(rolesTable.organizationId, organizationId),
      inArray(rolesTable.role, customRoleKeys),
    ),
});
```

Then `mergeCustomRolePermissions()` combines multiple custom roles into one effective permission map.

## API Authorization

API procedures use four gates in `packages/api/orpc/procedures.ts`.

| Procedure | Use for |
| --- | --- |
| `publicProcedure` | Public endpoints that do not require identity. |
| `protectedProcedure` | Signed-in user endpoints that are not necessarily scoped to studio tenant data. Payments use this because organization/user billing can vary by request. |
| `adminProcedure` | Platform admin endpoints. Checks `config.auth.platformAdminUserIds`. |
| `studioProtectedProcedure` | Tenant-scoped studio data. Requires session `activeOrganizationId` and verifies membership. |

Studio procedures should start here:

```ts
export const studioProtectedProcedure = protectedProcedure.use(
  async ({ context, next }) => {
    const organizationId = context.session.activeOrganizationId;

    if (!organizationId) {
      throw new ORPCError("FORBIDDEN", {
        message: "No active organization. Please select an organization.",
      });
    }

    const membership = await getOrganizationMembership(
      organizationId,
      context.user.id,
    );

    if (!membership) {
      throw new ORPCError("FORBIDDEN", {
        message: "Not a member of this organization",
      });
    }

    return next({
      context: {
        ...context,
        organizationId,
        membership,
      },
    });
  },
);
```

After tenant membership is proven, feature procedures can enforce resource permissions:

```ts
import { requirePermission } from "../../studio/lib/permissions";

await requirePermission(context, "booking", "create");
```

That helper calls `auth.api.hasPermission()` with request headers, so it evaluates the current Better
Auth role state.

## Platform Admin

Platform admin access is explicit user-id based:

```ts
admin({
  adminRoles: [],
  adminUserIds: config.auth.platformAdminUserIds,
});
```

The admin web layout repeats the same rule:

```ts
const isPlatformAdmin = config.auth.platformAdminUserIds.some(
  (adminUserId) => adminUserId === session.user.id,
);

if (!isPlatformAdmin) {
  redirect(appRedirectPath);
}
```

Do not grant platform admin through organization roles. Organization owner/admin is scoped to one
tenant; platform admin can see cross-tenant admin surfaces.

## Billing Side Effects

Auth hooks update seats when membership changes:

- Accepting an invitation updates subscription seats for that invitation's organization.
- Removing a member updates seats for that organization.
- Deleting a user or organization cancels active subscriptions before deletion.

This means auth changes can affect payments. If a change touches membership lifecycle, check both
`packages/auth/lib/organization.ts` and the payments handbook page.

## Common Change Patterns

Add a new protected studio endpoint:

```ts
export const createThing = studioProtectedProcedure
  .input(CreateThingSchema)
  .handler(async ({ context, input }) => {
    await requirePermission(context, "configuration", "create");

    return db.insert(things).values({
      organizationId: context.organizationId,
      ...input,
    });
  });
```

Add a new permission resource:

1. Add it to `statement` in `packages/auth/lib/permissions.ts`.
2. Decide which static roles receive which actions.
3. Update custom role UI if the matrix should expose it.
4. Use `requirePermission()` or `requireAnyPermission()` in API code.
5. Add capability flags only when navigation/header UI needs them.

Add a new organization lifecycle side effect:

1. Prefer Better Auth organization hooks in `packages/auth/auth.ts`.
2. Make the side effect idempotent.
3. Log success/failure with organization id, user id, and source.
4. Avoid throwing from best-effort studio sync unless the auth action must fail.

## Review Checklist

Before merging auth changes, verify:

- Public signup behavior matches `config.auth.enableSignup`.
- Auth redirects preserve `redirectTo` for protected pages.
- `/app` routes require a session in both proxy and server layout.
- Tenant data uses `studioProtectedProcedure`, not plain `protectedProcedure`.
- Organization-scoped reads verify membership before querying business tables.
- Resource mutations call `requirePermission()` or an equivalent explicit check.
- Platform admin still uses `platformAdminUserIds`, not org roles.
- Membership changes keep crew records and billing seats idempotent.
- Auth email failures are logged with enough context to debug delivery.
