## Workspace Contract

The monorepo is a pnpm workspace. These are the only first-class workspace roots:

```yaml
# pnpm-workspace.yaml
packages:
  - config
  - apps/*
  - packages/*
  - services/*
  - tooling/*
```

Every package should fit one of those lanes:

- `apps/*`: deployable web surfaces
- `packages/*`: reusable code imported as `@repo/*`
- `services/*`: long-running workers or standalone servers
- `tooling/*`: shared build/runtime tooling
- `config`: shared product configuration

Root scripts mostly delegate into Turbo:

```json
{
  "dev": "dotenv -c -- turbo dev --concurrency 15 ...",
  "build": "dotenv -c -- turbo build --filter=@repo/web...",
  "typecheck": "turbo type-check",
  "db:migrate": "pnpm --filter @repo/database migrate",
  "handbook:dev": "dotenv -c -- turbo dev --filter=@repo/handbook"
}
```

The practical rule: if a file needs to be imported by more than one app/service, it belongs in `packages/*`. If it only exists to make one deployed app work, keep it inside that app.

## Root Files

| File | Owns | Notes |
| --- | --- | --- |
| `package.json` | top-level scripts and pinned package manager | Uses `pnpm@10.23.0`; do not swap package managers |
| `pnpm-workspace.yaml` | workspace membership | Add new workspaces here only when adding a new app/package/service lane |
| `turbo.json` | task graph and cache outputs | `dev` and `start` are persistent; `build` outputs `dist/**` and `.next/**` |
| `tsconfig.json` | root TS inheritance | Extends `@repo/tsconfig/base.json` |
| `biome.json` | lint/format behavior | Astro files are excluded from Biome checks |
| `.env.example` | public env contract | New env vars should be added here |
| `.vercel/project.json` | local Vercel link | Currently points to the web project; do not use it for handbook deployment |

Generated/local folders to ignore during code review:

- `.next/`, `.turbo/`, `node_modules/`, `dist/`
- `apps/*/.next`, `apps/*/.turbo`, `services/*/dist`
- `apps/handbook/.source` is generated by Fumadocs
- `.vercel` is local project linking, not source

## Apps

### `apps/web`

Main Studio SaaS product. It owns:

- Next.js App Router routes in `apps/web/app`
- product UI and app-specific hooks in `apps/web/modules`
- API route entrypoints in `apps/web/app/api`
- Playwright tests in `apps/web/tests`
- client provider wiring in `apps/web/modules/shared/components`

Use `apps/web/app` for route files only:

```txt
apps/web/app
  auth/                         # auth pages
  (saas)/app/layout.tsx          # authenticated app gate
  (saas)/app/[organizationSlug]  # organization workspace routes
  api/[[...rest]]/route.ts       # Hono/oRPC API adapter
```

Use `apps/web/modules` for feature implementation:

```txt
apps/web/modules/saas/studio
  components/  # UI for studio workspace
  hooks/       # client hooks and param helpers
  lib/         # app-only helpers
```

Example: a new organization-scoped bookings view usually touches:

```txt
apps/web/app/(saas)/app/[organizationSlug]/bookings/...
apps/web/modules/saas/studio/components/...
packages/api/modules/bookings/router.ts
packages/database/drizzle/schema/studio.ts
```

### `apps/marketing`

Astro marketing site. It is separate from the product app. Biome is disabled for `apps/marketing/**/*.astro`, so use the marketing package's own checks when changing it.

```json
{
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "type-check": "astro check"
  }
}
```

Do not import product app internals from marketing. Shared brand constants can move to `config` or a small package if both apps need them.

### `apps/handbook`

Internal documentation site using Next.js + Fumadocs. It owns:

- MDX content in `apps/handbook/content/docs`
- Fumadocs source config in `apps/handbook/source.config.ts`
- generated search route in `apps/handbook/app/api/search/route.ts`

Use it for humans. Do not treat it as a dumping ground for generated API reference until we intentionally decide whether Mintlify is needed.

## Shared Packages

### Product/Core Packages

| Package | Responsibility | Common Imports |
| --- | --- | --- |
| `@repo/api` | Hono app, oRPC routers, webhooks, OpenAPI generation | `@repo/auth`, `@repo/database`, providers |
| `@repo/auth` | Better Auth config, org hooks, permissions, invitation-only plugin | `@repo/database`, `@repo/mail`, `@repo/payments` |
| `@repo/database` | Drizzle client, primary schema, migrations, query helpers | `drizzle-orm`, `pg`, `@repo/env` |
| `@repo/payments` | billing provider boundary, checkout/customer helpers, webhook handling | `@repo/database`, `@repo/env`, `@repo/logs` |
| `@repo/env` | environment validation | used before DB/provider initialization |
| `@repo/config` | product configuration and typed config | imports `@repo/env` |

### Provider/Utility Packages

| Package | Responsibility |
| --- | --- |
| `@repo/mail` | transactional email rendering/sending |
| `@repo/storage` | file storage provider boundary |
| `@repo/sms` | SMS provider, templates, phone/send utilities |
| `@repo/google-calendar` | OAuth, token crypto, calendar/ICS helpers |
| `@repo/logs` | structured logger |
| `@repo/i18n` | locale config/translations |
| `@repo/utils` | cross-package utilities |
| `@repo/editor` | editor-related shared code |

### WhatsApp Packages

WhatsApp is split from the main schema/provider packages:

| Package | Responsibility |
| --- | --- |
| `@repo/whatsapp-core` | provider-neutral WhatsApp types/contracts |
| `@repo/whatsapp-db` | WhatsApp Drizzle schema and migrations |
| `@repo/whatsapp-providers` | Cloud API provider implementation |
| `@repo/whatsapp-outbox` | package exists in the repo but currently has no active source tree in the first-level map |

`packages/database/drizzle/schema/index.ts` re-exports `@repo/whatsapp-db` so the main `db` client can use WhatsApp tables through `db.query.*`.

### UI And Tooling Packages

`@repo/ui` owns shared shadcn/Radix-style primitives:

```txt
packages/ui/src/components/button.tsx
packages/ui/src/components/dialog.tsx
packages/ui/src/components/table.tsx
packages/ui/src/styles/globals.css
```

Use `@repo/ui` for generic primitives. Keep product-specific components in `apps/web/modules/saas/*`.

`tooling/typescript` owns shared TS configs:

```json
// tooling/typescript/nextjs.json
{
  "extends": "./base.json",
  "compilerOptions": {
    "jsx": "preserve",
    "module": "esnext",
    "lib": ["dom", "dom.iterable", "esnext"]
  }
}
```

`tooling/tailwind` owns shared theme files. `tooling/scripts` owns operational scripts like deadline reminders and user creation.

## Services

Services are not UI packages. They should have explicit start/dev scripts and should do one operational job.

| Service | Role | Key State |
| --- | --- | --- |
| `services/calendar-worker` | polls calendar sync jobs and syncs Google Calendar/ICS/email invites | `calendarSyncJobs`, `shootCalendarEvents`, `googleCalendarConnections` |
| `services/sms-worker` | claims SMS outbox rows and sends via MSG91 | `smsOutbox` |
| `services/whatsapp-worker` | sends WhatsApp outbox messages through Cloud API | `waOutbox`, `waMessages`, `waAccounts` |
| `services/whatsapp-bridge` | Hono placeholder API for WhatsApp session bridge | currently returns `not_implemented` for session actions |

Worker code should not depend on `apps/web`. If a worker needs logic from the app, move that logic to a shared package first.

## Where To Put New Code

### New Page Or Route

Put route entry in `apps/web/app`.

```txt
apps/web/app/(saas)/app/[organizationSlug]/shoots/page.tsx
```

Put substantial UI under `apps/web/modules/saas/studio`.

```txt
apps/web/modules/saas/studio/components/shoots/shoots-view.tsx
apps/web/modules/saas/studio/lib/shoots-api.ts
```

### New API Procedure

Add a router under `packages/api/modules/<domain>/router.ts`, then register it in `packages/api/orpc/router.ts`.

```ts
// packages/api/orpc/router.ts
export const router = publicProcedure.prefix("/api").router({
	shoots: shootsRouter,
});
```

Use `studioProtectedProcedure` for organization-scoped studio data.

### New Table

Add schema to the domain file that owns it:

- auth/session tables: `packages/database/drizzle/schema/auth.ts`
- organization/core billing tables: `core.ts`
- studio domain tables: `studio.ts`
- integrations: `integrations-google-calendar.ts`
- outbox-specific tables: `sms.ts` or WhatsApp schema package

Then run:

```bash
pnpm db:generate
pnpm db:migrate
```

### New Worker

Create a new service only when runtime behavior is independent from web request/response.

```txt
services/<name>-worker
  package.json
  tsconfig.json
  src/index.ts
```

Add package dependencies directly to the service. Do not import `apps/web/modules`.

## Import Rules

Good imports:

```ts
import { db } from "@repo/database";
import { auth } from "@repo/auth";
import { Button } from "@repo/ui/components/button";
```

Avoid imports that cross ownership boundaries:

```ts
// Avoid: shared package depending on app internals
import { something } from "apps/web/modules/saas/studio/lib/something";

// Avoid: worker depending on web UI or app-only helpers
import { getSession } from "apps/web/modules/saas/auth/lib/server";
```

If you want to share code across app/API/worker, extract it into `packages/*`.

## Review Checklist

Before approving structural changes:

- Does the file live in the owner that will maintain it?
- Does it introduce an app-to-app or worker-to-app dependency?
- Is reusable business logic in `packages/*`?
- Are generated files ignored?
- If a new workspace was added, is `pnpm-workspace.yaml` still correct?
- If a new task was added, does `turbo.json` know the output/cache behavior?
- If a new env var was added, is `.env.example` updated?
