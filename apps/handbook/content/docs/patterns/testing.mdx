## What Testing Owns

Testing in this repo is layered by ownership boundary:

- lint and format checks prove code style and import hygiene
- TypeScript checks prove package contracts across the monorepo
- Vitest and Node tests prove isolated package behavior
- Playwright proves user-facing web flows
- smoke tests prove small integration surfaces that are hard to unit-test
- CI proves the minimum gate expected before merge

The main rule: test at the lowest layer that catches the failure. Use Playwright for user journeys, package tests for business rules, and worker tests for queue/job behavior.

## Standard Gates

Use these before handing off broad changes:

```bash
pnpm lint
pnpm check
pnpm typecheck
pnpm build
```

Use the handbook-specific gates after changing this site:

```bash
pnpm handbook:typecheck
pnpm handbook:build
```

Use environment validation when setup, deploy, or CI behavior changes:

```bash
pnpm env:check
```

`pnpm env:check` validates the core variables required by `packages/env`: `DATABASE_URL`, `BETTER_AUTH_SECRET`, and `NEXT_PUBLIC_SITE_URL`.

## Playwright

The web app uses Playwright from `apps/web/playwright.config.ts`.

Important defaults:

- test directory: `apps/web/tests`
- base URL: `http://localhost:3000`
- setup project: files matching `*.setup.ts`
- browser project: desktop Chromium
- CI retries: `1`
- CI workers: `1`
- traces: on first retry
- videos: retained on failure
- reporter: HTML report

Playwright loads `../../.env.local` from the web app directory. Keep test-only values local and never commit secrets.

The Playwright web server command builds and starts the app:

```bash
pnpm --filter web run build && pnpm --filter web run start
```

Run the interactive E2E UI while developing a flow:

```bash
cd apps/web
pnpm e2e
```

Run CI-style E2E before merging user-facing route or workflow changes:

```bash
pnpm --filter @repo/web e2e:ci
```

## PR CI

`.github/workflows/validate-prs.yml` runs on pull requests to `main`.

The current workflow has two jobs:

- `lint`: installs Biome and runs `biome ci .`
- `e2e`: installs dependencies, generates database artifacts, runs `pnpm env:check`, runs `pnpm --filter web e2e:ci`, then uploads `apps/web/playwright-report`

The workflow injects CI environment values for:

- `DATABASE_URL`
- `BETTER_AUTH_SECRET`
- `NEXT_PUBLIC_SITE_URL`

CI does not currently run the full root `pnpm typecheck` or `pnpm build:all` gate. Run those locally when a change touches shared packages, build configuration, database schema, or worker code.

## Test Selection

For a web route, component, or workflow change:

```bash
pnpm --filter @repo/web type-check
pnpm --filter @repo/web e2e:ci
```

For API router or domain logic changes:

```bash
pnpm --filter @repo/api test
pnpm --filter @repo/api type-check
```

For schema or query changes:

```bash
pnpm db:generate
pnpm typecheck
pnpm --filter @repo/api test
```

For SMS queue/provider changes:

```bash
pnpm --filter @repo/sms test
pnpm --filter @repo/sms-worker test
pnpm --filter @repo/sms-worker test:integration
```

For calendar sync changes:

```bash
pnpm --filter @repo/calendar-worker test
pnpm --filter @repo/calendar-worker type-check
```

For email rendering or invitation flows:

```bash
pnpm --filter @repo/mail test
pnpm --filter @repo/mail type-check
```

For handbook changes:

```bash
pnpm handbook:typecheck
pnpm handbook:build
```

## Regression Rule

For bugs, add a regression test when the behavior has a stable test boundary.

Good regression boundaries:

- a pure helper in `packages/api`
- schema validation behavior
- worker queue selection or retry logic
- payment catalog or checkout status mapping
- redirect sanitization
- notification recipient rules
- route access rules
- E2E flow where the bug only appears with browser state

Avoid broad E2E tests for behavior that a package test can prove faster and more precisely.

## Writing New Tests

Prefer this pattern for package tests:

```ts
import { describe, expect, it } from "vitest";

import { deriveStudioPrefix } from "./derive-studio-prefix";

describe("deriveStudioPrefix", () => {
	it("normalizes organization names into stable prefixes", () => {
		expect(deriveStudioPrefix("Rakesh Studio")).toBe("rakesh-studio");
	});
});
```

Prefer this pattern for Playwright route tests:

```ts
import { expect, test } from "@playwright/test";

test("redirects signed-out users to auth", async ({ page }) => {
	await page.goto("/studio/acme");

	await expect(page).toHaveURL(/auth/);
});
```

Keep fixtures small and name the business behavior being protected. A test name should explain the regression without opening the implementation.
